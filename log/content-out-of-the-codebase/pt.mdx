Corrigir um erro de digitação virava commit no repositório da aplicação. É um
incômodo pequeno, e incômodo pequeno que se repete é o que vale a pena resolver.

## O problema de verdade

Código e texto mudam em ritmos completamente diferentes. Eu mexo no layout deste
site talvez uma vez por mês. Mexo nas palavras dele várias vezes por semana —
uma frase mais afiada, uma descrição de projeto que envelheceu mal, um post novo.

Com os dois no mesmo repositório, o que muda rápido arrasta o que muda devagar.
Toda correção de texto aparece no mesmo histórico das refatorações de
componente, e cada uma gera um deploy. O histórico deixa de ser o registro de
como o software mudou e vira o registro de mim editando prosa.

## O que eu fiz

O conteúdo foi para um repositório público próprio. Três tipos de coisa moram lá
— meu histórico profissional, os textos de projeto e os posts — em markdown, uma
pasta por item, um arquivo por idioma.

O repositório do site nunca busca isso em runtime. Quando eu mergeio na `main` do
repositório de conteúdo, o CI dele chama um deploy hook, o site builda, e o texto
novo está no ar como HTML estático. Visitante nenhum encosta no GitHub. Se o
GitHub cair, o site não percebe, porque o GitHub só participa enquanto o build
roda.

## A parte que eu não esperava que importasse

O schema.

Como o conteúdo fica num repositório próprio, alguma coisa precisa conferi-lo
antes de ele chegar ao site — senão um campo faltando vira mistério no build em
vez de PR vermelha. Então o frontmatter é validado contra um schema, no CI, em
toda pull request.

Esse portão acabou valendo mais que a separação em si. As tags vêm de um
vocabulário fechado, então `nextjs`, `next-js` e `next.js` não conseguem virar
três nomes para a mesma coisa. Todo item precisa existir em inglês. Um post não
consegue referenciar um projeto que não existe. Nada disso depende de eu estar
atento num dia corrido.

## O que custa

Publicar agora custa um build — um ou dois minutos até as palavras estarem no ar.
Decidi que prefiro pagar isso a ter o site dependendo em silêncio de um serviço
externo a cada visita.

E há um segundo repositório para manter na cabeça. Esse custo é real, e o que o
torna suportável é a fronteira ser óbvia: se é texto, vai para lá; se renderiza
texto, fica aqui.
