## Why it exists

Job boards are a firehose. Most listings are noise for any given person, and the
signal decays fast — a good match found three days late is a match someone else
already took. I wanted the filtering to happen while I slept, and I wanted to
know when it broke.

## How it works

The pipeline has four stages, orchestrated by Kestra:

1. **Collect.** Scheduled scrapers pull listings from a handful of sources and
   normalize them into a single shape before anything else touches them.
2. **Deduplicate.** The same role gets posted to several boards under slightly
   different titles. A content hash plus a fuzzy title match collapses them.
3. **Classify.** Each surviving listing goes to an LLM through OpenRouter with a
   rubric — seniority, stack overlap, remote policy, red flags in the wording.
   The model returns a score and a one-line reason.
4. **Alert.** Anything above the threshold gets pushed to me with the reason
   attached, so I can tell within seconds whether the classifier was right.

PostgreSQL holds both the listings and the classification history. Keeping the
history is what makes the classifier auditable: when a score looks wrong, I can
see what the model saw.

## What made it interesting

**Cost was a design constraint, not an afterthought.** The whole thing runs on a
free-tier ARM VPS. That budget rules out keeping a model resident, so
classification is a per-item API call with aggressive caching — the dedup stage
exists partly to stop paying twice for the same listing.

**Classifier drift is real.** The same prompt against the same listing does not
score identically across model versions. Pinning the model helped; keeping the
scoring history is what let me notice the problem at all.

**Failure has to be loud.** A scraper that silently returns zero results looks
exactly like a quiet day on the job market. Every stage reports a count, and a
count of zero where there is usually a number is treated as a failure, not as
an empty result.
